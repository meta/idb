# Physical-device HID

`device.hid.tap(x:y:duration:)` sends one physical-device tap. Coordinates are display points. An absent or zero duration adds no intentional hold; a positive duration holds after the start call returns.

`device.hid.touch(try DeviceHIDTouchSequence(events))` sends one complete down/move/up recipe. Events are explicit `.down(x:y:)`, `.move(x:y:)`, `.up(x:y:)`, and `.delay(seconds)`. The sequence is validated before preparation: at most 256 events, one down, a final up matching the last position, finite nonnegative coordinates and delays, and less than five seconds of combined holds. It is not a live stream or a cross-call held contact. Coordinates are normalized once using one fresh metadata snapshot.

## Structure

The companion buffers the existing HID stream through successful EOF before selecting an operation. A legacy single-tap shape still uses `DeviceTapRequest` and `tap`. Repeated wire DOWN events become position updates in a complete touch recipe. One existing swipe message produces the constant-speed simulator recipe, including its duplicate endpoint and delay distribution; this does not promise the simulator's scrolling inertia on a phone. Oversized swipes are rejected rather than truncated. No protocol or Python CLI changes are needed. Accessibility `ui scroll` is a separate semantic action and is not replaced with a coordinate gesture; wheel/vendor events, buttons and multi-contact gestures remain unsupported here.

The lateral library follows the simulator command / operation / transport split. `DeviceHIDCommands` is cached on the concrete `Device`, holds it weakly, and owns local busy and uncertain state. `DeviceHIDOperation` owns one contact plan and its cleanup. `DeviceDigitizerHIDTransport` contains the typed private calls. Unlike the simulator transport, it does not reconnect, reset a cached connection, or expose generic disconnect.

Preparation resolves the selected device's exact UUID and normalizes display-point coordinates without private CoreDevice calls. It requires matching device and display metadata, rejects ambiguous identity or unsupported geometry and orientation, and preserves an absent or zero hold duration without adding a delay. Both queries must return successful JSONv5 with the expected command and device selector. The producer version is required diagnostic metadata, not a release allowlist; the loaded frameworks are validated separately.

Details and display queries run concurrently as owned subprocesses with ten-second query waits. Failure or cancellation joins both owned processes before removing their private output directory. Failed subprocess diagnostics include a bounded stderr tail; a secondary directory-removal error is logged without replacing the primary failure. The immutable prepared coordinates have no timestamp expiry. Preparation does not monitor display changes or guarantee that rotation, dimensions, or display configuration remain unchanged after the reads.

The caller must complete the runtime gate before constructing the private transport. Discovery requires exactly one current `RemoteDevice` with the prepared UUID; names, enumeration order, and ECID are not selectors. Before admitting start, the operation rechecks cancellation and its execution budget. Prepared coordinates are never refreshed during the contact; end uses the last admitted coordinate from that immutable recipe.

## Contact and lifetime

Native synchronous work uses a dedicated queue, not a Swift cooperative thread. The operation owns an assertion acquired with empty state/capability requirements; it never calls `RemoteDevice.connect`, `disconnect`, or `releaseAllAssertions`. Empty requirements do not prove readiness: digitizer construction can still fail.

Start is recorded as admitted before calling the native helper. Every send uses a nil second point, `.none` edge, and `.mainScreen` target. A tap's point never changes. A touch recipe advances through its prevalidated positions only while the operation remains admitted; it records each possibly delivered position before invoking that send. Normal completion lifts at the last position. Cancellation or failure lifts at the last admitted position, never a future planned one. An absent or zero duration adds no intentional hold; a positive duration holds after the start call returns. A thrown start or position still allows one matching end after the send has returned. No end overlaps a blocked send, and an uncertain end is never retried. One barrier follows the end attempt after it returns, including a throwing end. Cancellation, assertion invalidation, and the deadline share the same end claim.

The input operation has a ten-second execution budget and a five-second cleanup reserve. The complete contact's combined holds must fit strictly within the remaining budget after reserving that headroom, or preparation fails before input without quarantine when owned cleanup completes normally. The reserve is admission accounting, not a timer that abandons cleanup or a bound on blocked SDK work. Recipe count, coordinate and duration bounds still apply.

Monotonic deadlines are checked at admission, return processing, and final publication; timers only wake the operation. Error summaries are materialized outside state locks, and removed native references and cancellation captures remain retained until after lock exit. The operation joins expected native calls, acquisition and factory callbacks, observation, and claimed cancellation requests. It completes the owned end attempt and barrier before releasing only its own assertions and discarding its caller-side capability reference. Publication waits for owned release and discard to return. Clean late setup or cancellation does not itself quarantine; actual send or cleanup failures, unexpected completions, and assertion invalidation after input do. The first typed error or cancellation is preserved, with secondary cleanup failures carried in `DeviceHIDError.cleanupFailed(cause:failures:)`. Late acquisition results are released, and late factory results cannot reopen the operation.

The runtime preflight has a separate ten-second wait bound; cancellation or timeout cannot proceed from it into private input construction.

A native send/cleanup error, unexpected completion, or assertion invalidation after input admission quarantines subsequent input on this cached command, including an admitted request still in metadata or runtime preparation. Every uncertain final result synchronously applies quarantine before it is published. There is no reset/retry API. The state is local to this `Device`, not a cross-process input-ownership mechanism. Caller authorization and selection of a benign UI belong outside this library.

Neither `Progress.cancel`, task cancellation, nor the execution deadline terminates blocked SDK work. The operation remains pending until that work and its owned cleanup return; a blocked start receives one matching end only after start returns, and an attempted end is never replayed. Admission stays busy while that work is unfinished. An owned, supervised process is required when a hard local lifetime bound is needed. Dropping the caller's digitizer reference does not close the implementation cached by `RemoteDevice`. Process exit is not a remote cleanup acknowledgment.

Success means that local start, end, barrier, and owned release calls returned. It does not prove remote delivery, released physical contact, or a visible UI effect.

## Private runtime and export

The private Swift interface is resilient, without invented `Sendable` conformances or raw enum values. The gate requires native arm64 macOS 26.6 or newer and CoreDevice/CoreDeviceUtilities 651.13.5 or newer, comparing each framework's Mach-O source version numerically and rejecting missing or malformed metadata. There is no exact OS-build, file-hash or historical-UUID allowlist. Each installed arm64 slice's `LC_SOURCE_VERSION` and `LC_UUID` are read from the same binary snapshot. Every required symbol must resolve from its expected framework, and its loaded source version and UUID must match that snapshot and meet the minimum. An installation replacement cannot lend its version to an already-loaded older image. These checks do not guarantee private-API ABI or behavior compatibility on newer versions. Synchronous calls use `FBObjCExceptionGuard`; that synchronous guard cannot span the async Swift digitizer factory.

The private Swift implementation and import are compiled only for arm64; other architectures have a throwing unsupported-runtime transport and no private Swift references. Private Swift references and framework linkage must remain weak so unsupported hosts can load unrelated capabilities without idb constructing private metadata. `LC_LOAD_WEAK_DYLIB` still permits dyld to load and initialize an installed framework and its dependencies before command preflight; weak linkage is not deferred loading. The gate requires symbols visible through the binary's weak linkage; matching files on disk are not sufficient. The stub preserves CoreDevice's install name and its CoreDeviceUtilities re-export. Exported Xcode and SwiftPM builds require the private Swift module and weak stub as well as Buck builds.

The symbol catalogue covers named weak references in the linked binary, not every descriptor or witness reached through those references. A feature adds a newly referenced symbol alongside its first use. The binary regression compares that catalogue with the test bundle's private weak imports.

Unit tests exercise production image and metadata validation and the command and operation through initializer-injected native calls: admission reserve, timestamp-free prepared points, fixed payloads, contact races, joined late completions and blocked calls, typed cleanup failures, owned cleanup, quarantine-before-publication, and real `Device` cache retention. These tests do not constitute physical input or UI verification.
