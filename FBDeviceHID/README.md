# Physical-device HID

`device.hid.tap(x:y:duration:)` sends one physical-device tap. Coordinates are display points. An absent or zero duration adds no intentional hold; a positive duration holds after the start call returns.

`device.hid.touch(try DeviceHIDTouchSequence(events))` sends one complete bounded recipe of sequential, nonoverlapping down/move/up contacts. Events are explicit `.down(x:y:)`, `.move(x:y:)`, `.up(x:y:)`, and `.delay(seconds)`. The entire sequence is validated before preparation: at most 256 events across all contacts and pauses, each up matching its last position, finite nonnegative coordinates and delays, and less than five seconds of combined holds and inter-contact pauses. It starts with down and ends with up; no leading or trailing pause is accepted. It is not a live stream, arbitrary simultaneous multi-finger input, or a cross-call held contact. All coordinates are normalized once using one fresh metadata snapshot. Physical multi-tap and application double-tap recognition remain **unverified**; unit coverage proves local sequencing, not gesture recognition or exact remote timing.

`device.hid.touch(try .pinch(x:y:scale:duration:radius:))` sends one bounded two-finger gesture. The points stay symmetric on the horizontal axis, following the simulator recipe's ten-point sampling delta, minimum two interpolation steps, duplicate endpoint and delay distribution. Both points are normalized from the same portrait metadata snapshot. The expanded samples and delays fit the existing 256-event cap, with total duration less than five seconds; oversized recipes and nonfinite, off-display or coincident points are rejected, not clamped. Finger count is fixed from start through every position and end. Physical pinch recognition and two-finger behavior are **unverified**. This is neither arbitrary multi-finger input nor an atomic remote-delivery guarantee. The companion accepts one existing pinch wire message after successful EOF. Zero duration and radius retain the wire defaults of 0.5 seconds and 100 display points; negative or nonfinite values are rejected rather than defaulted. Pinch cannot be mixed with other events in the same request.

`device.hid.button(.home, duration:)` sends one bounded button down/optional-hold/up. The supported identities are `.home`, `.volumeUp`, and `.volumeDown`. Preparation binds fresh physical-device details to the selected UDID and CoreDevice UUID; it does not require display geometry. Button and touch calls share busy admission and sticky quarantine. Native page/code getters are resolved only inside the guarded transport after runtime preflight. Success still means local native returns, not physical button effects, volume step/routing, or remote release acknowledgment. Power/lock/side, Action, Siri, Apple Pay, play/pause, eject, and arbitrary usage codes are not enabled.

`device.orientation.current()` reads physical orientation; `device.orientation.set(_:)` sets one of portrait, portraitUpsideDown, landscapeLeft or landscapeRight. Reads also preserve unknown, faceUp and faceDown. The dedicated `idb rotation [ORIENTATION]` command uses these APIs; the legacy `idb ui rotate` HID encoding remains unsupported on physical devices. Rotation does not enable rotated touch coordinates: touch preparation still requires the verified portrait basis.

Orientation uses owned `devicectl device orientation get/set` subprocesses, not additional private Swift ABI. Each result must be successful JSONv5 from a named producer, echo the exact owned command arguments, and identify the CoreDevice UUID bound by fresh physical-device details. SET uses named physical directions and validates the returned current and non-flat orientations against the request. Orientation lock rejects SET before mutation. Success reports Apple's receipt, not completed animation or application layout.

Orientation operations share the cached HID command's busy admission and sticky uncertainty. They hold admission through all owned-process and metadata cleanup, without retaining the `Device`. Cancellation before SET admission is nonmutating. After SET admission, an operation error or cancellation is reported as possibly applied and quarantines further input, including cancellation observed after a valid receipt. A temporary-directory removal error alone is logged; it does not replace a successful receipt or the primary typed error. There is no retry, reverse rotation or reset. Each CLI phase has a bounded wait; cancellation terminates only its owned child. A process exit is not evidence that an already-dispatched remote mutation was undone.

## Structure

The companion buffers the existing HID stream through successful EOF before selecting an operation. A legacy single-tap shape still uses `DeviceTapRequest` and `tap`. Repeated wire DOWN events while a contact is active become position updates; a DOWN after a matching UP begins the next sequential contact. Existing Python multi-tap streams (including inter-contact delays) form one complete bounded recipe and one shared ownership scope, not separate RPCs or independent operations. A malformed later contact, stream failure, or cancellation at EOF rejects the whole request before input. One existing swipe message produces the constant-speed simulator recipe, including its duplicate endpoint and delay distribution; this does not promise the simulator's scrolling inertia on a phone. Oversized swipes are rejected rather than truncated. No protocol or Python CLI changes are needed. Accessibility `ui scroll` is a separate semantic action and is not replaced with a coordinate gesture; wheel/vendor events and arbitrary multi-finger gestures remain unsupported here; the bounded pinch recipe is the only two-finger operation. Button requests accept only one matching down/optional-delay/up pair for Home, volume up, or volume down through the same successful-EOF boundary.

The lateral library follows the simulator command / operation / transport split. `DeviceHIDCommands` is cached on the concrete `Device`, holds it weakly, and owns local busy and uncertain state. `DeviceHIDOperation` owns one bounded contact plan and its cleanup. `DeviceHIDTransport` contains the typed private calls. Unlike the simulator transport, it does not reconnect, reset a cached connection, or expose generic disconnect.

Preparation resolves the selected device's exact UUID without private CoreDevice calls. Touch preparation additionally requires matching display metadata, rejects ambiguous geometry or orientation, and normalizes display-point coordinates once. An absent or zero hold duration adds no delay. Required queries must return successful JSONv5 with the expected command and device selector. The producer version is required diagnostic metadata, not a release allowlist; the loaded frameworks are validated separately.

For touch input, details and display queries run concurrently as owned subprocesses with ten-second query waits. Button preparation queries only details. Failure or cancellation joins the owned processes before removing their private output directory. Failed subprocess diagnostics include a bounded stderr tail; a secondary directory-removal error is logged without replacing the primary failure. Prepared input has no timestamp expiry. Preparation does not monitor display changes or guarantee that rotation, dimensions, or display configuration remain unchanged after the reads.

The runtime gate precedes idb's explicit private metadata construction and calls; it is not a loader-ordering guarantee. Discovery requires exactly one current `RemoteDevice` with the prepared UUID; names, enumeration order, and ECID are not selectors. Before admitting start, the operation rechecks cancellation and its execution budget. Prepared coordinates are never refreshed during the contact; end uses the last admitted coordinate from that immutable recipe.

## Contact and lifetime

Native synchronous work uses a dedicated queue, not a Swift cooperative thread. The operation owns an assertion acquired with empty state/capability requirements; it never calls `RemoteDevice.connect`, `disconnect`, or `releaseAllAssertions`. Empty requirements do not prove readiness: digitizer construction can still fail.

Start is recorded as admitted before calling the native helper. Single-finger sends use a nil second point; bounded pinch sends both points through the existing typed overload with the same phase, `.none` edge and `.mainScreen` target. Both last-admitted points are recorded before invoking the native call and used together for cleanup. One native call does not prove atomic remote delivery or that both physical fingers were released. Button sends use the same semantic button identity for down and up. A tap's point never changes. A touch recipe advances through its prevalidated positions only while the operation remains admitted; it records each possibly delivered position before invoking that send. Normal completion lifts at the last position. The next contact cannot start until the previous end returns normally and its inter-contact pause elapses. This orders local native calls; neither end nor barrier is a remote UP acknowledgment. Cancellation or failure lifts only the last possibly active contact, at its last admitted position, never a future planned one or an already-ended earlier contact. An absent or zero duration adds no intentional hold; a positive duration holds after the start call returns. A thrown start or position still allows one matching end after the send has returned. No end overlaps a blocked send, and an uncertain end is never retried. One final barrier follows the last admitted end attempt after it returns, including a throwing end; the obligation survives advancing to a later contact. Cancellation, assertion invalidation, and the deadline share the same end claim.

The input operation has one ten-second execution budget and one five-second cleanup reserve for the entire recipe, not fresh budgets per contact. Every start admission requires all remaining holds and inter-contact pauses to fit strictly within the remaining budget after reserving that headroom. Refusal before any input is a preparation failure; after any earlier input it is an execution-deadline failure. Completed contacts are not undone or replayed, and their pending barrier is drained before release even if a later contact is refused. The reserve is admission accounting, not a timer that abandons cleanup or a bound on blocked SDK work. Recipe count, coordinate and duration bounds still apply.

Monotonic deadlines are checked at admission, return processing, and final publication; timers only wake the operation. Error summaries are materialized outside state locks, and removed native references and cancellation captures remain retained until after lock exit. The operation joins expected native calls, acquisition and factory callbacks, observation, and claimed cancellation requests. It completes the owned end attempt and barrier before releasing only its own assertions and discarding its caller-side capability reference. Publication waits for owned release and discard to return. Clean late setup or cancellation does not itself quarantine; actual send or cleanup failures, unexpected completions, and assertion invalidation after input do. The first typed error or cancellation is preserved, with secondary cleanup failures carried in `DeviceHIDError.cleanupFailed(cause:failures:)`. Late acquisition results are released, and late factory results cannot reopen the operation.

The runtime preflight has a separate ten-second wait bound; cancellation or timeout cannot proceed from it into private input construction.

A native send/cleanup error, unexpected completion, or assertion invalidation after input admission quarantines subsequent input on this cached command, including an admitted request still in metadata or runtime preparation. Every uncertain final result synchronously applies quarantine before it is published. There is no reset/retry API. The state is local to this `Device`, not a cross-process input-ownership mechanism. Caller authorization and selection of a benign UI belong outside this library.

Neither `Progress.cancel`, task cancellation, nor the execution deadline terminates blocked SDK work. The operation remains pending until that work and its owned cleanup return; a blocked start receives one matching end only after start returns, and an attempted end is never replayed. Admission stays busy while that work is unfinished. An owned, supervised process is required when a hard local lifetime bound is needed. Dropping the caller's digitizer reference does not close the implementation cached by `RemoteDevice`. Process exit is not a remote cleanup acknowledgment.

Success means that local start, end, barrier, and owned release calls returned. It does not prove remote delivery, released physical contact, or a visible UI effect.

## Private runtime and export

The private Swift interface is resilient, without invented `Sendable` conformances or raw enum values. The gate requires native arm64 macOS 26.6 or newer and CoreDevice/CoreDeviceUtilities 651.13.5 or newer, comparing each framework's Mach-O source version numerically and rejecting missing or malformed metadata. There is no exact OS-build, file-hash or historical-UUID allowlist. Each installed arm64 slice's `LC_SOURCE_VERSION` and `LC_UUID` are read from the same binary snapshot. Every required symbol must resolve from its expected framework, and its loaded source version and UUID must match that snapshot and meet the minimum. An installation replacement cannot lend its version to an already-loaded older image. These checks do not guarantee private-API ABI or behavior compatibility on newer versions. Synchronous calls use `FBObjCExceptionGuard`; that synchronous guard cannot span the async Swift digitizer factory.

The private Swift implementation and import are compiled only for arm64; other architectures have a throwing unsupported-runtime transport and no private Swift references. Private Swift references and framework linkage must remain weak so unsupported hosts can load unrelated capabilities without idb constructing private metadata. `LC_LOAD_WEAK_DYLIB` still permits dyld to load and initialize an installed framework and its dependencies before command preflight; weak linkage is not deferred loading. The gate requires symbols visible through the binary's weak linkage; matching files on disk are not sufficient. The stub preserves CoreDevice's install name and its CoreDeviceUtilities re-export. Exported Xcode and SwiftPM builds require the private Swift module and weak stub as well as Buck builds.

The symbol catalogue covers named weak references in the linked binary, not every descriptor or witness reached through those references. A feature adds a newly referenced symbol alongside its first use. The binary regression compares that catalogue with the test bundle's private weak imports.

Unit tests exercise production image and metadata validation and the command and operation through initializer-injected native calls: admission reserve, timestamp-free prepared points, fixed payloads, contact races, joined late completions and blocked calls, typed cleanup failures, owned cleanup, quarantine-before-publication, and real `Device` cache retention. These tests do not constitute physical input or UI verification.
