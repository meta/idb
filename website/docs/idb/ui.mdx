`idb ui` is the command group for everything that reads or drives the screen. It covers two kinds of operation that are easy to confuse:

- **Accessibility operations** ask the target's accessibility system what is on screen, and act on the *elements* it reports. `describe-all`, `describe-point`, `describe`, `scroll` and `set-value` are always accessibility operations; `tap` can be one.
- **HID operations** synthesize the events a physical finger, keyboard or button would produce. They operate on coordinates, not elements.

Accessibility operations are currently supported on iOS Simulators only. HID operations work on Simulators, and a subset works on Devices.

## Addressing the screen

Most of the group accepts a **target**, and there are three ways to name one:

| Target | Written as | Meaning |
|--------|-----------|---------|
| A point | `X Y` — two integers | A coordinate in the screen's points coordinate system, with the origin at the top left |
| A marker | a single string | The first element whose `--match-key` attribute *contains* this string |
| The frontmost app | omitted | The whole foreground application. Only where the command's target is optional |

Matching is a substring match, not equality, so `General` matches an element labelled `General Settings`. It is case-sensitive unless `--ignore-case` is passed, on reads and on marker writes alike.

Two integers are always read as a point. Quote a marker that looks like a coordinate pair:

```
# The element at (12, 40)
idb ui describe-point 12 40
# The element labelled "12 40"
idb ui describe '12 40'
```

`--match-key` chooses which attribute a marker is matched against. It defaults to `AXLabel`, and accepts `AXLabel`, `AXUniqueId`, `AXValue`, `title`, `role`, `role_description`, `subrole`, `help` and `placeholder`.

`--depth` bounds how far into the element tree a marker search descends, defaulting to `10`. Raise it for a marker nested inside a deep hierarchy; lower it to make a search over a large screen cheaper.

## Reading the screen

The three read commands differ only in what they are asked about — they share their options, their output schema, and the backend that serves them.

### `idb ui describe-all`

Describes every element of the frontmost application.

```
idb ui describe-all
```

The output is JSON on a single line. Pipe it through [`jq`](https://stedolan.github.io/jq/) to read it:

```
$ idb ui describe-all | jq '.[] | select(.AXLabel != null) | {AXLabel, type, frame}'
{
  "AXLabel": "General",
  "type": "Button",
  "frame": { "y": 264, "x": 20, "width": 362, "height": 44 }
}
{
  "AXLabel": "Accessibility",
  "type": "Button",
  "frame": { "y": 308, "x": 20, "width": 362, "height": 44 }
}
```

`--key` restricts which attributes are reported, and is repeatable. A read asks the application only for the attributes it reports, so narrowing a whole-screen read to the attributes you need is faster than reading everything and discarding most of it:

```
idb ui describe-all --key AXLabel --key frame
```

### `idb ui describe-point X Y`

Describes the single element at a point — a hit test.

```
$ idb ui describe-point 201 286 | jq '{AXLabel, type}'
{
  "AXLabel": "General",
  "type": "Button"
}
```

In the `default` and `nested` formats a whole-screen read emits an array where this emits a bare object, or `null` when nothing is at the point. `--format complete` always emits an array, whichever command produced it.

### `idb ui describe MARKER`

Describes the single element matching a marker.

```
$ idb ui describe General | jq '{AXLabel, AXUniqueId, type}'
{
  "AXLabel": "General",
  "AXUniqueId": "com.apple.settings.general",
  "type": "Button"
}
```

Match against an attribute other than the label with `--match-key`:

```
idb ui describe com.apple.settings.general --match-key AXUniqueId
```

### Options shared by the read commands

| Option | Applies to | Description |
|--------|-----------|-------------|
| `--api {ax,ax-coresimulator,axbridge}` | all three | Which backend serves the read: `ax` and `ax-coresimulator` read on the host, `axbridge` in the guest. See [FBSimulatorAX](fbsimulatorax.mdx#backends) |
| `--format {default,nested,complete}` | all three | The output format. See [FBSimulatorAX](fbsimulatorax.mdx#output-formats) |
| `--client-type CLIENT` | all three | The assistive client the read claims to be: `xctest` and the other automation clients get the full automation tree, the rest the VoiceOver-style tree. Unset claims none. See [Requesting clients](fbsimulatorax.mdx#requesting-clients) |
| `--nested` | all three | Deprecated alias for `--format nested` |
| `--key KEY` | all three | Report only this attribute; repeatable |
| `--profile` | all three | Collect timings and counts for the read, reported in the `complete` format. See [FBSimulatorAX](fbsimulatorax.mdx#reading-profile) |
| `--collect-frame-coverage` | all three | Collect screen-coverage ratios for the read's element frames, reported in the `complete` format |
| `--match-key KEY` | `describe` | Attribute the marker is matched against, default `AXLabel` |
| `--depth N` | `describe` | Maximum tree depth searched for the marker, default `10` |

## Waiting for an element

`idb ui wait MARKER` polls for a case-sensitive substring match, using `AXLabel` by default:

```
idb ui wait General --timeout 10 --poll-interval 0.5 --json
idb ui wait com.apple.settings.general --match-key AXUniqueId --json
```

A match exits successfully and prints `{"found": true}` with `--json`. A timeout exits with an error and prints `found: false` plus an `error` message naming the searched key and marker. The JSON `error` contains only the timeout explanation; observed values appear separately in `diagnostics`. Without `--json`, the CLI formats those values beneath the explanation.

With `--api axbridge` (the default) or a host backend (`--api ax`, `--api ax-coresimulator`), timeout `diagnostics.unmatched_values` contains only nonmatching values of the searched key from the final poll: labels for a label search, identifiers for an identifier search. It contains no other element attributes and requires no additional tree read. The sample holds at most 50 values, each limited to 200 characters; `diagnostics.truncated` indicates omitted text. Older companions and backends that do not supply diagnostics omit the field.

For `axbridge`, `diagnostics.truncated` also records a truncated tree read. If its final poll ended in a retryable read failure, `diagnostics.read_error` explains why and the values are empty. The `ax` backend propagates read failures as errors instead.

## Waiting for the UI to settle

`idb ui quiet` reports whether the frontmost app's UI is quiet: its main run loop is idle and it has no animations in flight. It exits successfully when quiet and with status 1 when busy.

```
idb ui quiet
idb ui quiet 30
idb ui quiet 0
idb ui quiet 30 --watch
idb ui quiet 30 --bundle-id com.apple.Preferences --json
```

With a timeout, the command waits up to that many seconds and exits successfully as soon as the UI is quiet, or with status 1 if the timeout elapses first. A timeout of `0` waits for as long as it takes. With `--watch`, the command keeps reporting events once the UI is quiet, until the timeout elapses (or, with `0`, until interrupted), then exits successfully if the last state was quiet and with status 1 otherwise. The companion streams state changes as they happen; the CLI does not poll. Each event is printed as it arrives, one JSON object per line with `--json`: `state` (with `busy`, `settling` or `quiet`, and the busy signals), `touches_completed`, `target_changed` when the frontmost app changes, `target_exited`, and `timed_out`.

| Option | Description |
| --- | --- |
| `--watch` | Keep reporting events once the UI is quiet, until the timeout elapses. Requires a timeout |
| `--pid PID` / `--bundle-id ID` | Watch this app instead of following the frontmost app. The command fails if it exits |
| `--busy-threshold-ms MS` | How long a busy signal must persist before it counts, default `20` |
| `--quiet-window-ms MS` | How long the UI must stay idle before it is quiet, default `250`. When reporting the current state it defaults to `0`, so the answer is immediate |

## Acting on elements

These commands resolve a target through the accessibility system and then perform the action the platform itself would perform. They are not synthesized touches: an accessibility press activates the element directly, so it does not depend on where the element is on screen at the moment of the press.

### The backend an action is served by

`--api` selects the backend, as it does for the read commands, and every acting command accepts it. Unlike a read, an action defaults to `axbridge`: a host backend cannot see across a process boundary, so a marker that `describe --api axbridge` resolves is one a host backend would fail to find. Web content in Safari is the clearest case — every element on the page belongs to another process — but it holds for any out-of-process view.

```
# The guest reader sees the link inside Safari's web content process
idb ui describe 'GETTING STARTED' --match-key AXLabel --api axbridge
# ...and so does the tap, without naming a backend
idb ui tap 'GETTING STARTED' --match-key AXLabel
# The backend the actions used before, still one flag away
idb ui tap General --api ax
```

One consequence worth knowing: an `axbridge` action asserts automation mode device-wide, exactly as an `axbridge` read does — see [FBSimulatorAX](fbsimulatorax.mdx#automation-mode).

### `idb ui tap`

`tap` can be either a HID operation or an accessibility operation, depending on how the target is addressed:

```mermaid
flowchart TD
    tap["idb ui tap TARGET"] --> kind{"How is the target addressed?"}
    kind -- "X Y coordinates" --> hid["Synthesized touch — HID"]
    kind -- "X Y with --api ax, ax-coresimulator or axbridge" --> press["Accessibility press"]
    kind -- "a marker" --> press
    kind -- "any target with --expected-value" --> press
```

```
# Coordinate tap, delivered as a synthesized touch
idb ui tap 201 286
# The same coordinate, delivered as an accessibility press of whatever is under it
idb ui tap 201 286 --api ax
# A marker — always an accessibility press
idb ui tap General
```

`--api` does double duty here. `hid` is the synthesized touch; `ax`, `ax-coresimulator` and `axbridge` are accessibility presses, served by the backend they name. So naming a backend for a coordinate moves it onto the accessibility path, as `--api ax` always has.

A marker is always resolved through the accessibility system; passing `--api hid` with one is rejected rather than silently ignored.

A marker write aims at the matched element's frame centre without consulting `interactable` or `occluded_by`: it taps where the element is, not whether anything covers it. To check reachability first, read the element — `describe-point` on its centre, or `describe` with `--key interactable` — and only then act.

`--duration` holds the touch down for a given time, and is only meaningful for a coordinate touch. An accessibility press is instantaneous, so `--duration` is rejected there rather than silently ignored.

`--expected-value` guards the tap. The element must report that value for `--expected-key` (default `AXLabel`) or the tap is refused, leaving the screen where it was:

```
idb ui tap com.apple.settings.general --match-key AXUniqueId --expected-value General
```

Because the guard has to read the element before acting, passing `--expected-value` moves even a coordinate tap onto the accessibility path.

### `idb ui scroll DIRECTION [TARGET]`

Scrolls an element, or the frontmost application when no target is given.

```
# Scroll the frontmost app down
idb ui scroll down
# Scroll a specific element
idb ui scroll up 'Notification Center'
idb ui scroll left 201 286
```

`DIRECTION` is one of `up`, `down`, `left`, `right` or `visible`. `visible` scrolls the target into view rather than in a direction. `--match-key`, `--depth` and `--ignore-case` apply to a marker target.

A scroll is not an action on the element it names. iOS models it as `accessibilityScroll:`, which UIKit bubbles *up* from that element to the nearest scrollable container — which is why naming a row inside a list scrolls the list, and why the application element, having no container above it, cannot be scrolled at all. A scroll with no target therefore aims at the centre of the frontmost application, where its scroll view is.

### `idb ui set-value TARGET --value VALUE`

Sets an element's accessibility value — the direct way to fill a text field or move a slider, with no keyboard involved.

```
idb ui set-value 'Search' --value 'hello world'
idb ui set-value 201 286 --value 'hello world'
```

Unlike `scroll`, a target is required: there is no sensible value to set on a whole application. `--match-key`, `--depth` and `--ignore-case` apply to a marker target.

## Synthesizing input

These commands emit HID events. They take coordinates, not elements.

### `idb ui multi-tap X Y`

Taps repeatedly at a point, defaulting to a double tap.

```
idb ui multi-tap 201 286
idb ui multi-tap 201 286 --count 3 --pause 0.05
```

`--count` sets the number of taps (default `2`), `--pause` the gap between them in seconds (default `0.1`), and `--duration` how long each touch is held.

### `idb ui swipe X_START Y_START X_END Y_END`

Touches down at the start point, moves to the end point, and lifts.

```
idb ui swipe 100 500 100 100
```

The touch is moved in steps; `--delta` sets the distance in points between successive touch points along the line, and `--duration` sets how long the whole gesture takes.

### `idb ui pinch X Y SCALE`

A two-finger pinch centred on a point. A scale above `1.0` zooms in, below `1.0` zooms out.

```
# Zoom in around the centre of the screen
idb ui pinch 201 437 2.0
# Zoom out slowly, with the fingers starting further apart
idb ui pinch 201 437 0.5 --duration 1.0 --radius 150
```

`--radius` is the initial distance of each finger from the centre in points (default `100.0`), and `--duration` the length of the gesture in seconds (default `0.5`).

### `idb ui button BUTTON`

Presses a hardware button: one of `APPLE_PAY`, `HOME`, `LOCK`, `SIDE_BUTTON`, `SIRI`, `PLAY_PAUSE`, `VOLUME_UP`, `VOLUME_DOWN` or `EJECT`. `EJECT` on a focused text field hides or re-shows the software keyboard without ending editing.

```
# Send the target to the lock screen
idb ui button LOCK
# Hold the side button
idb ui button SIDE_BUTTON --duration 2
# Toggle the software keyboard
idb ui button EJECT
```

### `idb ui remote ACTION`

Sends a Siri Remote action for tvOS focus navigation: one of `up`, `down`, `left`, `right`, `select` or `menu`. Arrows move focus, `select` activates the focused element, and `menu` goes back.

```
idb ui remote down
idb ui remote select
```

### `idb ui text TEXT [--layout LAYOUT]`

Types text, as a hardware keyboard would. It takes a single argument, so text containing spaces must be quoted.

```
idb ui text 'hello world'
idb ui text 'héllo' --layout French
```

Each character becomes the key presses that produce it on the simulator's hardware keyboard layout, whichever layout the simulator is set to. An accented character can arrive in a canonically equivalent form. `--layout` names a layout to type on instead, such as `US` or `French`.

The layout is read from the simulator's keyboard settings. An app keeps the layout it was launched with, so after changing the simulator's keyboards, relaunch the app or pass `--layout`.

Text the layout cannot type fails the command before anything is typed, naming the offset of the first character it cannot type. The offset counts characters (grapheme clusters), starting at 0. Input methods that convert key presses into other text, such as Japanese, Chinese and Korean, are not covered. [`idb ui set-value`](#idb-ui-set-value-target---value-value) sets such text with no keyboard involved.

With a companion that does not advertise typing text, the client sends the key presses of a US keyboard and refuses any other `--layout`.

### `idb ui key KEYCODE`

A short press of a single [USB HID keyboard usage code](https://usb.org/document-library/hid-usage-tables-16).

```
# Return
idb ui key 40
# Command-A
idb ui key 4 --command
```

Modifiers are held for the duration of the press: `--shift`, `--control`, `--option`, `--command`, and `--tab` for [iOS Full Keyboard Access](https://support.apple.com/en-gb/guide/iphone/ipha4375873f/ios). `--duration` sets how long the key is held.

### `idb ui key-sequence KEYCODE...`

Presses several keycodes in order.

```
idb ui key-sequence 4 5 6
```

### `idb ui rotate ORIENTATION`

Rotates the target to `PORTRAIT`, `PORTRAIT_UPSIDE_DOWN`, `LANDSCAPE_LEFT` or `LANDSCAPE_RIGHT`.

```
idb ui rotate LANDSCAPE_LEFT
```

### `idb ui shake`

Sends a shake gesture — the one that triggers "Shake to Undo", and the motion event many apps hang a debug menu off.

```
idb ui shake
```

## Building a loop

The read and act commands compose: read the screen, then address elements by marker rather than hardcoding coordinates that vary with device size and layout:

```
# Wait for a button to appear, then press it
until idb ui describe 'Get started' > /dev/null 2>&1; do sleep 0.5; done
idb ui tap 'Get started'

# Fill a field and submit, guarding that we are on the screen we think we are
idb ui set-value 'Email' --value 'user@example.com'
idb ui tap 'Continue' --expected-value 'Continue'
```

`--api axbridge` keeps the companion-owned reader warm between requests, including across separate `idb` invocations; see [FBSimulatorAX](fbsimulatorax.mdx#guest-backend---api-axbridge).
